# Research: End-to-End Production Flight Dispatch & Headless PX4 SITL (`008-e2e-prod-flight`)

## Decision 1: Headless PX4 SITL + Gazebo Harmonic without NVIDIA Runtime
- **Decision**: Run `drone_sim` (`autonomous_drone_env`) in headless mode (`HEADLESS=1`) by removing the `deploy.resources.reservations.devices` NVIDIA block in `docker-compose.yml` and updating `scripts/entrypoint_drone.sh` to run `HEADLESS=1 make px4_sitl gz_x500`.
- **Rationale**: Host WSL2 kernel (`6.6.114.1-microsoft-standard-WSL2`) lacks `nvidia-smi` and `nvidia-container-toolkit`. `PX4_SYS_AUTOSTART` / `make px4_sitl gz_x500` with `HEADLESS=1` runs full PX4 EKF2/commander/navigator physics and Gazebo Harmonic headless server without GPU/X11.
- **MAVLink Networking**: PX4 SITL broadcasts MAVLink on UDP port `14540` to `PX4_SIM_HOST_ADDR` or `edge_drone` on `c2-shared-net` (or `edge_drone` connects via `udpin://0.0.0.0:14540` with `drone_sim` targeting `edge_drone`, OR `drone_sim` + `edge_drone` share network / `PX4_MAVLINK_REMOTE` / `mavlink_router` — specifically, PX4 `gz_x500` sends offboard MAVLink to `127.0.0.1:14540` by default unless configured, OR `edge_drone` can use `network_mode: "service:drone_sim"`? Note: if `edge_drone` uses `network_mode: "service:drone_sim"`, both share `127.0.0.1:14540` AND `drone_sim` exposes `8090:8090` on `c2-shared-net`! Wait: `edge_drone` reaches `mosquitto:1883` and `minio:9000` on `c2-shared-net` through `drone_sim`'s `c2-shared-net` interface!).
  - **Best, cleanest Docker Compose pattern**: Give `drone_sim` `ports: ["8090:8090"]`? Or keep `edge_drone` on `c2-shared-net` and run `drone_sim` with `network_mode: "service:edge_drone"`!
  - Even simpler: If `drone_sim` has `network_mode: "service:edge_drone"`, then `edge_drone` keeps its exact service name (`edge_drone:8090`), ports (`8090:8090`), and `c2-shared-net` DNS (`mosquitto`, `minio`), while PX4 SITL inside `drone_sim` sends MAVLink UDP directly to `127.0.0.1:14540` where `isc_edge` (`MAVSDK_URL=udpin://0.0.0.0:14540`) is listening! Zero IP-lookup race conditions!

## Decision 2: Temporal Worker & `ProcessSmeacWorkflow` Dispatch
- **Decision**: Start an in-process `temporalio.worker.Worker` inside `src/uservice/main.py` lifespan (polling `ISC_TASK_QUEUE`, default `isc-smeac-queue`) with `ProcessSmeacWorkflow`, `parse_smeac_activity`, `safety_check_activity`, and a new `dispatch_edge_mission_activity`.
- **Rationale**: `POST /api/v1/swarms/{id}/orders` already launches `ProcessSmeacWorkflow` in Temporal, but previously no worker was running. Adding `dispatch_edge_mission_activity` completes the durable execution loop by posting parsed waypoints (`POST {endpoint_url}/navigate`) to `isc_edge` and marking `smeac_orders.status = "executed"`.
- **Alternatives Considered**: Direct HTTP call from `SmeacFacade` bypassing Temporal — rejected because Constitution & `006-remove-fallback-logic` mandate Temporal durable workflows.

## Decision 3: Swarm Endpoint Binding & Edge Context Sync
- **Decision**: Set `SWARM_DEFAULT_ENDPOINT=http://edge_drone:8090` in `docker-compose.yml` for `backend` (which `src/uservice/swarm/operations/create.py` already reads!). When `provision_swarm` registers a swarm (or when `dispatch_edge_mission_activity` dispatches), pass `swarm_id` and `project_id` to `isc_edge` (`POST /context` or in `POST /navigate` + `POST /target`) so `_telemetry_publisher` streams MQTT telemetry under the newly provisioned `swarm_id`!
- **Rationale**: In `src/edge/api/server.py`, `_telemetry_publisher` defaults to `SWARM_ID="swarm-edge-1"`. Dynamically updating `_telemetry_publisher.swarm_id` and `_telemetry_publisher.project_id` when a swarm is provisioned or navigated ensures live PX4 telemetry flows straight into `swarm_live_states` for that exact `swarm_id`.

## Decision 4: Edge `/navigate` Execution via MAVSDK
- **Decision**: Add `POST /navigate` to `src/edge/api/server.py` accepting `waypoints: list[Waypoint]` (`lat`, `lon`, `alt_m`), `command_id`, `swarm_id`, `project_id`. An async background task ensures `_drone` is armed and airborne (via `action.arm()`, `action.takeoff()`), then flies sequentially to each waypoint using `action.goto_location(lat, lon, target_abs_alt, 0.0)` until within arrival threshold or next order supersedes it.
